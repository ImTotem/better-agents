# 설명 양식

이 양식은 사용자에게 승인이나 방향 선택을 받으려고 물을 때만 쓴다. 그때는 답변, 앱의 요약 칸, 질문 창, 버튼에 모두 쓴다.

이유: 사용자는 개발자지만 내 작업 과정을 보지 못한다. 무언가를 정해 달라고 할 때는 한 번 읽고 무엇이 됐는지, 무엇을 골라야 하는지, 고르면 무슨 일이 생기는지 알아야 한다. 그 밖의 글까지 양식으로 쓰면 무겁고 길어진다(사용자, 2026-11-22: "설명 규칙은 나에게 승인이나 방향을 선택 받기 위해 질문할때에만 적용해라").

## 1. 글의 종류를 먼저 고른다

- **결정 요청**: 사용자에게 승인을 받거나 방향을 고르게 하는 글이다. 아래 보고 양식을 그대로 쓴다.
- **그 밖의 글**: 진행 상황, 정할 일이 없는 결과 알림, 사실 하나나 예/아니오를 묻는 질문의 답이다. 양식 없이 짧게 쓴다. 제목과 `무엇`/`예`/`영향` 항목을 쓰지 않는다. 짧은 답은 1~3문장이다.
- 두 종류 모두 4절의 말투와 낱말은 지킨다.

## 2. 보고 양식

```
## 지금 상황
<무엇이 어떻게 됐는지 1문장>. <사용자가 정할 일과 내 추천 1~2문장, 또는 "정하실 것은 없습니다.">

**<종류> 1: <요점을 담은 짧은 문장>**
- 무엇: <한 문장>
- 예: <사용자가 실제로 칠 명령이나 볼 장면, 그리고 그 결과 한 문장>
- 영향: <사용자에게 생기는 일 한 문장>

**<종류> 2: <요점을 담은 짧은 문장>**
- 무엇: …
- 예: …
- 영향: …

그 밖에 작은 것 <n>개가 있습니다. 원하시면 설명드리겠습니다.

## 정해 주실 것
- **<선택지 이름> (추천)**: 고르면 <일어나는 일>. 이유: <한 문장>.
- **<선택지 이름>**: 고르면 <일어나는 일>.

<질문 한 문장>
```

## 3. 양식의 각 부분

- `## 지금 상황`: 3문장 이내로 쓴다. 첫 문장은 결과, 다음은 사용자가 할 일과 내 추천이다.
- 항목 제목: `**<종류> <번호>: <요점 문장>**` 모양으로 쓴다. 종류는 "새 버그", "고친 것", "남은 것", "확인한 것"처럼 사용자가 바로 알아보는 말이다. 요점 문장은 주제가 아니라 결론을 담는다. 예: "고친 결과"가 아니라 "평범한 명령이 다시 통과합니다".
- 항목 본문: 언제나 `- 무엇:`, `- 예:`, `- 영향:` 세 줄이다. 줄마다 한 문장이다. 하위 목록은 만들지 않는다.
- 항목 수: 한 보고에 3개까지 쓴다. 나머지는 "그 밖에 작은 것 n개" 한 줄로 줄인다.
- 근거 한 줄: 확인한 방법이 있으면 항목 다음에 한 문장으로 쓴다. 예: "두 버그 모두 직접 재현해서 확인했습니다."
- `## 정해 주실 것`: 사용자가 정할 일이 있을 때만 쓴다. 추천 선택지를 맨 앞에 두고 이유를 붙인다. 선택지마다 "고르면 무슨 일이 일어나는지"를 쓴다.
- 마지막 줄: 질문 한 문장이다. 앞을 읽지 않아도 무엇을 고르는지 알 수 있게 쓴다.
- 앱이 요약 칸이나 질문 창을 따로 보여 주면: 요약은 `## 지금 상황`과 같은 낱말로 쓰고, 질문은 마지막 줄 질문과 같은 뜻으로 쓰고, 버튼은 선택지 이름을 그대로 쓴다.

## 4. 말투와 낱말

- 한국어로 쓴다. 코드, 명령, 파일 경로만 원래 글자 그대로 백틱 안에 쓴다.
- 대상은 뜻이 드러나는 한국어 이름으로 부른다. 예: "N1" 대신 "평범한 명령까지 막는 버그". 한 번 정한 이름은 끝까지 같게 쓴다.
- 전문용어는 쉬운 말로 바꾼다. 예: "fail-open" 대신 "오류가 나면 막지 않고 통과시킴", "글롭" 대신 "`*` 같은 와일드카드". 바꿀 수 없는 용어는 처음 나올 때 괄호로 뜻을 붙인다.
- 한 문장에는 생각 하나만 담는다. "이것", "그것" 대신 가리키는 대상을 쓴다.

## 5. 보내기 전 점검

1. 결정 요청이 아닌데 양식을 썼는가? 썼으면 양식 없이 짧게 고쳐 쓴다. 결정 요청이라면 `## 지금 상황`이 맨 앞에 있고 3문장 이내인가?
2. 모든 항목이 제목 한 줄과 `무엇`, `예`, `영향` 세 줄 모양인가?
3. 사용자가 쓴 적 없고 내가 풀어 쓰지도 않은 번호, 줄임말, 영어 용어가 남아 있는가? 남아 있으면 바꾼다.
4. 정할 일이 있으면 마지막 줄이 질문인가?
5. 이 대화를 처음 보는 개발자가 한 번 읽고 이해하는가?

## 지금 상황
플러그인 수정 중에 새 버그 2개가 생겼습니다. 실제로 써 보기 전에 이 버그들을 먼저 고칠지 정해 주세요. 저는 먼저 고치기를 추천합니다.

**새 버그 1: 평범한 명령까지 막습니다**
- 무엇: 설계 기록 폴더(`docs/architecture/.state`)를 지키는 규칙이 너무 넓어져서, 상관없는 파일 삭제까지 막습니다.
- 예: 프로젝트 맨 위 폴더에서 `rm -f *.o`를 실행하면 "설계 기록을 지우려 한다"며 막힙니다.
- 영향: 코드를 짜는 단계에서 에이전트가 자주 멈춰 작업이 진행되지 않습니다.

**새 버그 2: 다른 저장소 폴더 안에서는 보호가 꺼집니다**
- 무엇: 프로젝트 안에 별도 git 저장소가 있으면, 그 폴더 안에서는 플러그인이 설계 중인 프로젝트를 찾지 못합니다.
- 예: `vendor/lib` 안에서 `rm -rf ../../docs/architecture/.state`를 실행하면 막히지 않고 설계 기록이 지워집니다.
- 영향: 지켜야 할 설계 기록을 잃을 수 있습니다.

두 버그 모두 직접 재현해서 확인했습니다.

## 정해 주실 것
- **먼저 고치기 (추천)**: 고르면 두 버그를 고치고, 고친 부분을 다시 검사한 뒤 실제로 써 봅니다. 이유: 버그 1이 남아 있으면 써 보는 내내 막혀서 플러그인을 평가할 수 없습니다.
- **바로 써 보기**: 고르면 지금 상태로 설치해서 써 봅니다. 자주 막힐 수 있습니다.

새 버그 2개를 먼저 고칠까요, 아니면 지금 상태로 바로 써 볼까요?
