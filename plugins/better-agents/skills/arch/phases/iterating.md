# `iterating` 단계 (ADD 2~7단계, 반복마다)

`ga status`로 현재 반복 n을 확인한다. 이번 드라이버는 architecture.md 4절(현재 라운드의 반복 계획)에서 반복 n의 `high` 드라이버다. architecture.md 5절에 `### 반복 n: 목표` 소절(라운드 2부터 `### 라운드 r 반복 n: 목표`)을 만들고 순서대로 채운다.

1. **반복 목표**(ADD 2): 다룰 드라이버 ID와 목표 한 줄.
2. **세분화할 요소**(ADD 3): 첫 반복은 시스템 전체, 이후는 앞 반복의 요소 중 이번 드라이버와 관련된 것.
3. **설계 개념 비교와 결정**(ADD 4): 요소마다 실제로 성립하는 후보(참조 아키텍처, 패턴, 전술, 프레임워크, 외부 컴포넌트)를 **두 개 이상** 놓고, 연결된 드라이버의 시나리오와 측정 기준에 비추어 비교한다. 후보의 근거도 찾는다. 고른 것을 `ga_add`(kind `decision`)로 SKILL.md 3절 "항목 형식"대로 기록한다.
4. **요소, 책임, 인터페이스**(ADD 5): 요소마다 책임과 공개 인터페이스(연산, 입력과 출력, 오류)를 표로 쓴다.
5. **구조도**(ADD 6): 같은 소절에 mermaid 코드 블록으로 그린다. 요소 이름은 4의 표와 같게 쓴다.
6. **드라이버 분석**(ADD 7): 이번 드라이버와 영향받은 드라이버마다 `충족`, `부분`, `미충족`과 근거(DEC-n, 측정 기준과의 관계)를 표로 쓴다. 부분·미충족이면 이유와 다룰 반복을 적는다.
7. **검증과 승인**: SKILL.md 1절의 검증과 승인 절차 후 `GA 승인 반복`을 요청한다. 승인 조건(현재 라운드): 이번 반복의 결정 1개 이상, 이번 반복의 `high` 드라이버가 모두 이번 반복 결정의 `drivers`에 있음. 마지막 반복이 승인되면 `design-review`로 간다.

새로 생긴 가정과 질문도 SKILL.md 0절 규칙과 3절 "항목 형식"대로 기록한다. 새로 알게 된 드라이버는 `ga_add`(kind `driver`)로 추가하고, `high`면 현재나 남은 반복 번호를 준다.
