## 1. 의도와 이유

- **문제:** Claude는 큰 구조의 아키텍처 설계를 잘 못한다. (사용자)
- **목적:** 이미 생긴 실패를 사후에 막는 도구가 아니다. **처음부터 제대로 설계하게 만드는 도구**다. (사용자)
- **사용자의 설계 방식:**
  1. 어떤 기능을 만들지, 앞으로 어떤 기능이 추가될지 정한다.
  2. 가독성, 유지보수성, 확장성, 사용성, 개발 편의성 등 품질 요소를 모두 따진다.
  3. 아키텍처를 먼저 설계해 큰 뼈대를 잡는다.
  4. 그다음 세부 로직을 쓴다. (사용자)
- **기존 방법론과의 관계:** 위 순서는 SEI의 ADD 3.0(Attribute-Driven Design)과 대응한다. (확인: Cervantes·Kazman·Cai 2025, Figure 1)
- **브레인스토밍 중 드러난 핵심 결함:** Claude의 판단에 근거가 없다. 이 결함을 고치는 규칙은 아키텍처 설계 외의 작업에도 적용한다. (사용자)

## 2. 목표, 비목표, 반목표

### 목표
- **G1.** 아키텍처를 설계할 때 ADD 3.0 절차를 따르게 한다.
- **G2.** 모든 판단을 세 등급으로 나누고 근거를 기록하게 한다. 아키텍처 외 작업도 포함한다.
- **G3.** 해결되지 않은 가정이나 근거 누락이 있으면 다음 단계로 가지 못하게 **강제로** 막는다.
- **G4.** 결과물로 설계 문서와 코드 뼈대를 만든다. 구현 중 설계에서 벗어나면 문서를 함께 고친다.
- **G5.** 메인을 포함한 여러 모델로 이루어진 검증 패널이 근거의 **내용**을 검사한다.
- **G6.** 하네스와 모델에 묶이지 않는 구조로 만든다. v1은 Claude Code 어댑터만 만들지만, 다른 하네스 어댑터와 다른 회사 모델을 추가할 때 코어를 고치지 않아도 되어야 한다. (사용자)

### 비목표
- 시각 디자인. 별도 후속 프로젝트로 다룬다. (제안)
- 작은 수정이나 버그 수정에 설계 절차를 강제하는 것. 아키텍처 스킬은 명시적으로 호출할 때만 동작한다. (판단: 근거는 반목표 A4)
- 여러 모델이 경쟁하는 방식(arena)을 기본 흐름에 넣는 것. v1에서는 옵션으로도 넣지 않는다. (판단: 비용 문제, 확인: pstack 이슈 #436. 또한 ADD 논문은 LLM 하나와 사람의 협업만으로 효과를 확인함)
- v1에서 Claude Code 외 하네스의 어댑터를 구현하는 것. 다만 구조는 확장할 수 있어야 한다 (G6, 5.0절).

### 반목표: 작동하더라도 실패로 보는 것
- **A1. 가정으로 도망가기.** 근거를 찾지 않고 가정이나 질문으로 넘기는 것. (사용자 지적)
- **A2. 이상한 가정.** 간접 근거 없이 하는 가정. (사용자 지적)
- **A3. 형식만 채운 근거.** 칸은 채워졌지만 근거가 판단을 실제로 뒷받침하지 못하는 것.
- **A4. 무거워서 안 쓰게 되는 것.** (확인: pstack 이슈 #436, 작은 수정에도 스킬 읽기와 위임이 쌓여 비용이 커진 사례)
- **A5. 추측성 과설계.** 근거 없는 미래 기능에 대비해 구조를 키우는 것. (확인: pstack의 subtract-before-you-add 원칙이 경계하는 문제)
- **A6. API 과금 발생.** 이 도구가 부르는 모델 호출이 한 번이라도 API 단위나 토큰 단위로 과금되는 것. (사용자: 절대 배제)

## 3. 공통 규칙: 판단의 근거 등급

### 3.1 세 등급 (사용자)

| 등급 | 조건 | 처리 |
|---|---|---|
| 확정 | 직접 근거가 있다 | 완료 |
| 근거 있는 가정 | 직접 근거는 없고 간접 근거가 있다 | **미완료.** 사용자 확인이나 추가 조사로 직접 근거를 얻어야 완료된다 |
| 근거 없는 가정 | 근거가 없다 | **금지.** 대신 질문한다. 질문에도 탐색 기록을 붙인다 |

### 3.2 직접 근거로 인정하는 것 (제안)
1. 사용자가 말한 요구사항이나 결정
2. 대상 코드나 환경에서 확인한 사실 (`파일:줄`, 명령 출력)
3. 검증된 문헌이나 방법론 (출처 URL 또는 서지)
4. 측정이나 실험 결과

### 3.3 간접 근거로 인정하는 것 (사용자 예시 기반)
- 기존 코드의 관례
- 프레임워크 기본값
- 문헌상 일반적인 경우
- 사용자가 밝힌 목표에서 이끌어 낸 추론

### 3.4 기록 형식

| 대상 | 칸 |
|---|---|
| 결정 | 선택 \| 근거 (등급과 출처) \| 버린 대안과 버린 이유 |
| 가정 | 가정 내용 \| 간접 근거 \| 직접 근거 탐색 기록 \| 다른 가능한 가정과 버린 이유 |
| 질문 | 질문 \| 탐색 기록 \| 답에 따라 무엇이 바뀌는가 |

- 결정 형식의 출처: ADD 논문의 Step 4 표 "Selected design concept \| Rationale \| Discarded Alternatives". (확인: Cervantes 외 2025, Figure 3)
- 가정 형식의 출처: 사용자 지적. "다른 가능한 가정" 칸은 이상한 가정을 거르기 위한 것이다.

**원장에 무엇을 올리는가** (판단, 빌더 검토 Q10)
- **올리는 것:** 아키텍처상 의미 있는 결정, 모든 가정, 모든 질문
- **올리지 않는 것:** 그 밖의 판단. 대신 응답 안에서 근거를 표시한다(공통 규칙). 이렇게 해서 "모든 판단에 근거"를 지키면서 문서가 비대해지는 것을 막는다.

**대안이 없는 결정**
- 사용자 제약 때문에 강제된 결정은 버린 대안 칸에 `대안 없음: 사용자 제약 (출처)`라고 쓸 수 있다. 형식 검사는 이를 유효한 값으로 인정한다.
- 출처는 반드시 사용자 발언이어야 한다. 출처가 없으면 검증 에이전트가 반려한다.

### 3.5 탐색 범위: 어디까지 봐야 "찾아봤다"고 할 수 있는가 (판단)
탐색 기록에는 최소한 아래 범위를 본 결과가 들어가야 한다. 해당하지 않는 곳은 "해당 없음"과 그 이유를 적는다.
- 대상 프로젝트의 코드
- 프로젝트 문서: README, CLAUDE.md, `docs/`, 메모리 디렉터리
- 현재 대화
- 웹이나 문헌 (일반 지식에 관한 판단일 때)

근거: pstack 이슈 #59 4번. 프로젝트 규칙이 지정한 위치(메모리 디렉터리)를 보지 않고 "기록 없음"이라고 단정했는데, 실제로는 거기에 기록이 있었다.

### 3.6 미래 기능에도 등급을 적용한다 (제안)
- 사용자가 밝힌 로드맵에 있는 기능: **확정**
- 도메인 문헌상 흔한 확장: **근거 있는 가정** (확인을 받아야 함)
- 근거가 없는 기능: 설계에 **반영하지 않음**

반목표 A5(과설계)와 사용자가 말한 "추가될 기능 고려"를 하나의 규칙으로 함께 다룬다.

### 3.7 적용 범위와 강제 수준

| 범위 | 강제 수준 |
|---|---|
| 아키텍처 스킬 안 | 게이트로 강제 (5.5절) |
| 그 외 모든 작업 | 요청마다 규칙 문장을 주입. **강제는 불가능**하며 효과는 측정 대상 (6절) |

- **검토했지만 뺀 것:**
  - CLAUDE.md 규칙만 쓰는 방식: A보다 약하고 강제력이 없다.

## 5. 구성

### 5.0 구조 원칙: 코어와 어댑터 분리 (사용자 요구 G6에 대한 판단)
- **코어**는 하네스를 모른다. 코어가 하는 일:
  - 규칙 원문 보관
  - 상태, 원장, 검증 보고의 스키마
  - 게이트 판정
  - 형식 검사
  - 검증 패널 실행
  - 코어는 명령줄 도구(CLI)로만 호출된다.
- **어댑터**는 하네스마다 하나씩 둔다. 하네스의 이벤트(파일 쓰기 직전, 사용자 입력, 턴 종료, 세션 시작)를 코어 CLI 호출로 옮기는 일만 한다. 판단 로직을 어댑터에 두지 않는다.
- **선례:** pstack은 같은 스킬 묶음을 Claude Code, Codex, Copilot, OpenCode, Grok, Gemini 등에서 쓴다.
  - 방식: 공통 SKILL.md에 하네스별 매니페스트, 훅, 도구 대응 문서를 붙인다.
  - 확인: pstack-claude 저장소 파일 목록(`.codex-plugin/`, `.grok-plugin/`, `hooks/codex-hooks.json`, `opencode/index.js` 등)과 저장소 설명
- **모델 호출은 대칭이다.** 검증 패널의 각 모델은 "실행기(runner)"로 추상화한다.
  - 실행기는 같은 입력 묶음을 받아 같은 형식의 지적 목록을 돌려준다.
  - v1 실행기: `claude -p --model <모델> --allowedTools <읽기 전용 도구>` (확인: 이 기기의 `claude --help`에 `-p`, `--model`, `--allowedTools`가 있음)
  - `--bare`는 쓰지 않는다. 구독 인증을 읽지 않고 API 키를 요구하기 때문이다 (5.10절).
  - 이후 실행기: `codex`, `opencode` 등 각 CLI. 이 기기에는 `codex`와 `opencode`가 설치되어 있고, `gemini`와 `grok`은 없다.
  - 따라서 메인이 Claude든 GPT든, 실행기 목록만 바꾸면 서로를 검증자로 부를 수 있다.
- **어댑터별 강제력 차이:** 하네스마다 훅 기능이 다를 수 있다.
  - 어댑터는 네 가지 게이트(쓰기 차단, 사용자 입력 포착, 턴 종료 검사, 컨텍스트 주입) 중 무엇을 강제할 수 있는지 선언한다.
  - 강제할 수 없는 게이트는 약해진다는 것을 문서에 적는다.
  - (가정) pstack이 Codex, Copilot, OpenCode용 훅 파일을 가지고 있으므로 이 하네스들에도 훅 기능이 있을 것으로 본다. 어댑터를 만들 때 확인한다.

### 5.1 패키지 구조
ai-tools 저장소를 Claude Code 플러그인 마켓플레이스로 만든다. (확인: Plugins 레퍼런스 "Standard layout")
- 코어도 플러그인 디렉터리 **안**에 둔다. 플러그인 설치 시 그 디렉터리가 복사되므로, 밖에 두면 어댑터가 코어를 찾지 못한다. (판단)
- 같은 이유로 pstack도 모든 것을 `plugins/pstack/` 하나에 넣었다. (확인)

```
ai-tools/
├─ .claude-plugin/marketplace.json
└─ plugins/grounded-arch/
   ├─ core/                        # 하네스 무관
   │  ├─ rules/grounding.md        # 공통 근거 규칙 원문 (단일 원본)
   │  ├─ schema/                   # 상태, 원장, 검증 보고 스키마
   │  ├─ bin/ga                    # 코어 CLI: 상태 전환, 형식 검사, 게이트 판정, 검증 실행
   │  └─ verifier/                 # 검증 프롬프트, 입출력 규약, 실행기(runner)
   ├─ skills/                      # SKILL.md
   │  ├─ grounding/SKILL.md
   │  └─ design-architecture/SKILL.md
   ├─ .claude-plugin/plugin.json   # Claude Code 어댑터
   ├─ hooks/hooks.json             # Claude Code 어댑터: 이벤트마다 core/bin/ga 호출만 함
   └─ (이후) .codex-plugin/, opencode/ 등 다른 하네스 어댑터
```

### 5.2 공통 근거 규칙 주입
- **방식:** 플러그인 `hooks/hooks.json`의 UserPromptSubmit 훅이 `hookSpecificOutput.additionalContext`로 짧은 규칙을 넣는다. (확인: Hooks 레퍼런스)
- **적용 범위:** 플러그인 훅은 플러그인을 켜면 사용자 훅, 프로젝트 훅과 합쳐져 동작한다. 그래서 모든 작업에 적용되고, 이는 사용자 의도와 맞다. (확인: Plugins 레퍼런스)
- **분량:** 주입 문장은 짧게 쓴다. 10,000자를 넘으면 파일로 빠지고 앞부분 2,000자만 보이므로, 그보다 훨씬 짧아야 한다. (확인: Hooks 레퍼런스) 전문은 `grounding` 스킬에 둔다.
- **효과:** 아직 검증되지 않았다. (가정) 6절에서 측정한다.

### 5.3 아키텍처 설계 스킬: 단계

ADD 3.0의 단계 번호를 괄호로 함께 적는다.

| 단계(phase) | 하는 일 | 끝나는 조건 |
|---|---|---|
| `inputs` (ADD 1) | 설계 목적, 현재 기능, 미래 기능(3.6절 등급 적용), 품질 속성 시나리오와 우선순위, 고려사항, 제약을 정리한다. 이어서 반복 계획을 세운다: 반복마다 다룰 드라이버. 고우선 드라이버만 넣어 문서가 비대해지지 않게 한다 | 사용자 승인 |
| `iterating` (ADD 2~7을 반복) | 반복마다 아래를 수행한다 (표 아래 목록 참조) | 모든 반복이 끝남 |
| `design-review` | 설계 문서 전체를 검증 에이전트가 검사하고 사용자가 검토한다 | 사용자 승인 |
| `skeleton` | 폴더, 모듈, 인터페이스와 타입, 빈 함수를 만든다. 함수 본문은 미구현 표시만 둔다. 설계 요소와 코드 위치의 대응표를 문서에 넣는다 | 사용자 승인 |
| `implement` | 게이트를 해제한다. 설계에서 벗어나면 문서를 갱신하고 결정 기록을 추가하며 승인 여부를 기록한다. 승인되지 않은 이탈은 문서에 "미승인 이탈"로 보이게 남긴다 (확인: pstack architect 규칙) | 없음 |

`iterating` 단계의 각 반복:
1. 반복 목표 선정
2. 세분화할 요소 선택
3. 설계 개념 후보를 **두 개 이상** 비교하고 결정 표에 기록 (확인: pstack architect, ADD 논문 Step 4)
4. 요소, 책임, 인터페이스 정의
5. 구조도(mermaid)와 결정 기록. mermaid를 쓰는 이유: LLM이 PlantUML보다 mermaid를 더 잘 다뤘다 (확인: ADD 논문 4.1.1절)
6. 드라이버별 충족 여부를 충족, 부분, 미충족으로 근거와 함께 분석
7. 반복이 끝날 때마다 검증 에이전트 실행

- **품질 속성 시나리오의 형식:** 측정 가능한 응답 기준을 반드시 포함한다. (확인: ADD 논문 3절 "described as scenarios that include some metric")
- **문서는 하나만 쓴다.** 설계 문서는 `architecture.md` 하나다. (확인: ADD 논문 4절 "a single centralized architecture document")

### 5.3.0 `inputs` 단계는 요구사항만 다룬다 (사용자)
이 단계에서는 "무엇을, 왜"만 다루고 "어떻게"는 다루지 않는다. 세 가지 장치로 강제한다.
1. **코드 쓰기 금지:** G-write가 막는다.
2. **아키텍처 결정 금지:** 이 단계의 원장에는 아키텍처 결정 항목을 올릴 수 없다. 형식 검사로 강제한다.
   - 예외: 사용자가 준 제약(예: "DB는 PostgreSQL")은 **제약** 항목으로 기록할 수 있다. 출처는 사용자 발언이어야 한다.
   - 금지: Claude가 스스로 기술이나 구조를 고르는 것.
3. **섞임 검사:** 검증 에이전트가 입력 문서에 구조나 기술 선택이 섞여 있는지 검사한다 (5.6절 검사 항목 6).

**superpowers와의 관계**
- **호출 방식:** 아키텍처 작업은 사용자가 `/design-architecture`로 직접 호출한다.
- **brainstorming과의 충돌:** superpowers 자체 규칙에 "사용자 지시(direct requests 포함)가 스킬보다 우선"이라고 되어 있다. 그래서 직접 호출하면 brainstorming이 끼어들지 않을 것으로 본다.
  - 등급: 근거 있는 가정. 간접 근거는 using-superpowers 본문이다.
  - 확인 방법: 시범 평가 때 실제로 그런지 확인한다 (6절).
- **brainstorming 파일은 수정하지 않는다.** 남의 플러그인이라 업데이트할 때 덮어씌워질 것으로 본다.
  - 등급: 근거 있는 가정.
  - 간접 근거: pstack 안내문에 "설치된 플러그인 파일을 지워도 플러그인 업데이트가 되살린다"고 되어 있다.

### 5.3.1 기존 코드베이스 (사용자: 새 프로젝트와 기존 코드 둘 다 지원)
ADD는 기존 시스템을 설계 입력으로 받는 방식을 지원한다. (확인: ADD 논문 Figure 1 "existing system (brownfield development)")

- **모드 판정**
  - 대상 프로젝트에 소스 코드가 있으면 기존 코드 모드를 제안한다(환경 사실). 사용자가 확인한다.
- **`inputs` 단계에서 더 하는 일: 현재 구조 파악**
  - 현재 모듈, 의존 관계, 코드에 이미 들어 있는 설계 결정을 정리한다.
  - 각 항목은 `파일:줄` 근거가 붙은 **확정** 항목으로 원장에 올린다.
  - 코드만 보고 의도를 추정한 것은 **근거 있는 가정**으로 올린다. 예: "이 계층 분리는 테스트를 위한 것으로 보인다."
- **`skeleton` 단계**
  - 새로 생기거나 바뀌는 모듈과 인터페이스만 만든다.
  - 기존 코드를 옮기거나 이름을 바꾸는 것은 원장의 별도 **결정**으로 기록한다. 근거와 버린 대안을 함께 적는다.
  - 대응표에는 설계 요소마다 코드 위치와 구분(신규, 변경, 유지)을 적는다.
- **`skeleton` 단계의 검증** (판단: 뼈대 단계는 구조만 만들고 동작을 바꾸지 않는 단계이므로)
  - 뼈대를 만든 뒤에도 기존 빌드와 테스트가 통과해야 한다.
  - 검증 에이전트는 실제 명령 출력을 근거로 이를 확인한다.

### 5.4 산출물 (대상 프로젝트 안)
- `docs/architecture/architecture.md`: 사람이 읽는 단일 설계 문서
- `docs/architecture/.state/`: 기계가 읽는 상태
  - 현재 단계
  - 결정, 가정, 질문 원장(ledger). 항목마다 상태가 있다: 미해결, 질문함, 해결.
  - 승인 기록
  - 최신 검증 보고와, 그 보고가 검사한 문서 버전의 해시
- **제약:** 결정, 가정, 질문 목록의 원본은 한 곳에만 둔다. 문서와 원장이 따로 놀면 안 된다. 어느 쪽을 원본으로 할지는 빌더가 정하되, 훅 스크립트가 **결정적으로 파싱**할 수 있어야 한다.

### 5.5 게이트
게이트 훅은 스킬 머리말이 아니라 **플러그인 `hooks/hooks.json`**에 둔다.
- 이유: 설계는 여러 세션에 걸친다. 그런데 스킬 머리말의 훅은 그 세션에서 스킬을 호출해야만 켜진다(확인: Hooks 레퍼런스 "Hooks in skills and agents"). 그러면 새 세션에서 게이트가 꺼진 채로 코드를 쓸 수 있다. (판단, 빌더 검토 Q5)
- 모든 게이트는 현재 프로젝트에 `docs/architecture/.state`가 없거나 상태가 `paused`이면 즉시 통과한다. 파일이 있는지 한 번 보는 것뿐이라 매 호출 비용은 작다. (가정: 빌더가 실행 시간을 측정)
- `.state`가 있으면 SessionStart 훅이 현재 단계와 미해결 항목 수를 컨텍스트에 넣는다.
- **일시정지:** 사용자 전용 명령으로 일시정지하고 재개할 수 있다. 설계 도중에 관계없는 작은 수정이 필요할 때 쓴다 (비목표 "작은 수정에 절차 강제하지 않음").

**단계 전환은 앞으로만 가지 않는다** (판단, 빌더 검토 Q8)
- 사용자 명령으로 `design-review`나 `skeleton`에서 `iterating`으로 되돌릴 수 있다.
- `implement` 중에 새 기능이 들어오면, 같은 `architecture.md`에서 새 반복(round)을 시작한다. 근거: ADD 논문 3절은 이후 설계 라운드가 정제된 설계를 입력으로 받아 Step 1부터 다시 시작한다고 설명한다.

**G-write: 쓰기 게이트** (PreToolUse, `Write|Edit|MultiEdit|NotebookEdit`)

| 현재 단계 | 동작 |
|---|---|
| `inputs`, `iterating`, `design-review` | `docs/architecture/` 밖에 쓰는 것을 거부(deny)하고 이유를 돌려준다 |
| `skeleton` | 새 프로젝트: 허용한다. 기존 코드: 대응표에 "신규"나 "변경"으로 적힌 파일만 허용한다. 뼈대와 로직은 결정적으로 구분할 수 없으므로, 그 구분은 검증 에이전트와 사용자 검토가 맡는다 (판단) |
| `implement` | 관여하지 않는다 |

거부는 어떤 권한 모드에서도 적용된다. (확인: Hooks 가이드)

**G-bash: 셸 쓰기 게이트** (PreToolUse, `Bash`)
- 리다이렉션, `tee`, `sed -i`, `cp`, `mv` 등 파일 쓰기 패턴을 최선을 다해 검사한다.
- **알려진 한계:** 셸 명령이 무엇을 쓰는지 정적 분석으로 완전히 판정할 수는 없다. (판단)

**G-approval: 승인 게이트** (판단, 빌더 검토 Q1·Q2·Q6. 근거: 사용자 규칙 "가정이 남으면 다음 단계 불가", 사용자가 지적한 "가정으로 도망가기")
- **승인은 사용자만 할 수 있다.** UserPromptSubmit 훅이 사용자의 정해진 승인 문구를 감지해 승인 기록을 남기고, 단계는 그 기록에 따라서만 바뀐다.
- **승인 지점:** 입력 승인, 반복 종료 승인(반복마다), 설계 승인, 뼈대 승인.
- **승인 전제 조건.** 아래 중 하나라도 해당하면 훅이 승인을 거부하고(`decision: block`), 남은 항목 목록을 사용자에게 보여준다.
  - 원장에 미해결 항목이 있다. "질문함" 상태도 포함된다.
  - 검증 지적 중에 처리 결과가 없는 것이 있다.
  - 검증 보고의 해시가 현재 문서와 다르다.
- **일괄 승인 금지.** 승인 문구 하나로 남은 가정들을 한꺼번에 확인한 것으로 치지 않는다. 사용자는 항목 ID를 지정해 하나씩 답하거나 확인한다. 그 내용은 UserPromptSubmit 훅이 사용자 원문과 함께 기록하며, 이것이 직접 근거 1번(사용자 발언)이 된다.
- **사용자 확정은 훅만 기록한다.** 에이전트는 항목을 "사용자 확인으로 해결"로 직접 바꿀 수 없다. 에이전트가 직접 해결 처리할 수 있는 것은 코드, 문헌, 측정 같은 다른 직접 근거를 붙인 경우뿐이다.
- **쓰기 금지 대상:** 에이전트가 승인 기록, 단계 파일, 검증 보고를 쓰려고 하면 PreToolUse에서 거부한다. Bash 경로는 최선을 다해 막는다.
- **방어 대상:** 이 게이트들은 모델이 잊는 경우뿐 아니라 **규칙을 우회하는 지름길**까지 막는 것을 목표로 한다. (판단: 사용자가 지적한 우려가 모두 지름길 유형이었음)

**G-stop: 종료 게이트** (Stop)

설계 단계에서 원장에 **형식 오류**가 있으면 종료를 막고(`decision: block`), 무엇이 빠졌는지 이유로 돌려준다. 형식 오류는 다음과 같다.
- 결정에 근거나 버린 대안이 비어 있다.
- 가정에 간접 근거, 탐색 기록, 대안 칸 중 하나라도 비어 있다.
- 근거 없는 항목이 질문으로 바뀌지 않았다.

검증 보고의 최신 여부는 G-stop에서 보지 않고 **승인 시점(G-approval)에서만** 본다. 이유: 종료할 때마다 검사하면 매 턴 검증 에이전트를 돌려야 해서 비용이 폭증한다(반목표 A4). (판단, 빌더 검토 Q2)

**허용하는 경우:** 형식 오류가 없으면 종료를 허용한다. 남은 항목이 "질문함" 상태로 사용자 답을 기다리는 것은 정상적인 종료다.

**계속 막기:** 형식 오류가 남아 있으면 `stop_hook_active`가 참이어도 계속 막는다. 형식 오류는 에이전트가 직접 고치거나, 질문으로 바꿔서 해소할 수 있기 때문이다. 다만 Claude Code는 연속 8번 막히면 Stop 훅을 무시한다. (확인: Hooks 가이드) (판단, 빌더 검토 Q7)

### 5.6 검증 패널 (여러 모델)
- **입력:** `architecture.md`, 원장, 대상 코드 (읽기 전용)

**검사 항목**
1. 가정마다: 직접 근거를 찾을 수 있었는가? 실제로 탐색해서, 찾으면 위치를 제시하고 반려한다. (사용자 지적)
2. 가정마다: 간접 근거가 그 가정을 실제로 뒷받침하는가? (사용자 지적)
3. 결정마다: 근거가 결정을 뒷받침하는가? 버린 대안이 실제로 성립하는 대안인가? 허수아비 대안은 반려한다. (판단: 반목표 A3 대응)
4. 결정끼리 모순은 없는가? (확인: ADD 논문 5.3절. RecoveryManager가 문서 다른 곳과 맞지 않았던 사례)
5. 고우선 드라이버가 모두 어떤 결정에 연결되어 있는가? (확인: ADD 논문 Table 4, 많은 드라이버가 "부분 충족"이었음)
6. `inputs` 단계의 산출물에 Claude가 고른 구조나 기술 선택이 섞여 있지 않은가? (사용자 조건, 5.3.0절)

**지적 규칙:** 지적마다 증거를 붙인다(`파일:줄`, 출처, 탐색 결과). 증거가 없는 지적은 버린다. (pstack interrogate 원칙을 차용)

**실행 방식** (판단: G6, 그리고 빌더 검토 Q6의 위조 방지)
- 메인 에이전트는 `ga verify`만 호출한다. 이 명령이 패널의 각 실행기를 돌리고, 결과를 합쳐 검증 보고를 **스크립트가 직접** 쓴다.
- 에이전트는 `.state` 아래에 쓸 수 없다 (G-approval).
- **도구:** 실행기에는 읽기, 검색, 웹 검색 도구만 허용한다.

**(가정) 중첩 실행 문제**
- Claude Code 세션 안에서 Bash로 `claude -p`를 다시 실행해도 인증과 권한이 정상적으로 동작하는지는 확인되지 않았다.
- 구현 계획의 첫 작업에서 확인한다.
- 실패하면 Claude 어댑터에 한해 대안을 쓴다: 서브에이전트로 검증하고, 그 출력을 SubagentStop 훅이나 Agent 도구의 PostToolUse 훅으로 포착해 기록한다.

**대화 기록 전달:** 검증 패널에는 대화 기록 경로도 넘긴다. 어댑터가 사용자 입력 이벤트 때 훅 입력의 `transcript_path`를 `.state`에 기록하고, `ga verify`가 이를 실행기에 넘긴다. 사용자 발언을 근거로 든 항목과, 3.5절의 "현재 대화" 탐색 범위를 검사하기 위해서다. (판단, 빌더 검토 Q6)

**지적의 처리** (판단, 빌더 검토 Q3)
- 지적은 기계가 읽을 수 있는 형식으로 낸다.
- 지적마다 처리 결과를 남긴다:
  - **수정함**
  - **반박함:** 증거를 첨부한다
  - **사용자 기각**
- 처리 결과가 없는 지적이 있으면 승인할 수 없다 (G-approval).
- "반박함"은 승인할 때 사용자가 판정한다. 검증 에이전트도 틀릴 수 있기 때문이다.

**패널 구성** (사용자: 메인을 포함한 여러 모델. 모델마다 잘하는 것이 다르기 때문)
- 모델 목록은 설정 파일로 정한다.
- v1 기본 목록은 메인 모델을 포함한 Claude 계열 여러 모델이다. 이후 다른 회사 모델의 실행기를 추가한다.
- **간접 근거:** pstack 실측에서 같은 지시를 받아도 하네스와 모델에 따라 따르는 비율이 크게 달랐다. Claude 메인 세션은 19%, Codex는 약 73%가 플레이북까지 따라갔다 (#264).

**지적 통합** (확인: pstack interrogate "the verdict keeps every verified finding")
- 증거가 확인된 지적은 모델과 관계없이 **모두** 남긴다 (합집합).
- 같은 원인을 가리키는 지적은 하나로 합친다.

**모델별 기여 기록**
- 지적마다 어느 모델이 찾았는지 기록한다.
- 이 기록으로 "모델마다 잘하는 것이 다르다"를 측정으로 확인하고, 모델 조합을 조정하는 근거로 쓴다. (판단)

**비용**
- 비용은 모델 수만큼 늘어난다 (반목표 A4).
- 패널 크기는 설정으로 조절한다.
- 시범 평가에서 모델별로 검증된 지적 수와 비용을 함께 기록한다.

**호출 강제:** G-approval이 검증 보고가 최신인지 검사하므로, 검증 호출을 빠뜨리면 승인을 받을 수 없다.

**참고:** 대안(서브에이전트 방식)을 쓰게 될 경우, 플러그인 서브에이전트는 머리말의 `hooks`를 무시한다는 점에 유의한다. 포착 훅은 플러그인 `hooks.json`에 둔다. (확인: Hooks 레퍼런스)

### 5.7 언어
스킬과 에이전트 본문은 한국어로 쓴다. (판단: 사용자의 기존 스킬이 모두 한국어임, `~/.claude/skills/*/SKILL.md`)

### 5.8 런타임 제약 (이 기기 기준)
| 도구 | 상태 | 판단 |
|---|---|---|
| `bash` | 3.2.57 | 훅 스크립트에 사용 |
| `jq` | 1.7.1, `/usr/bin/jq` (시스템 기본) | 훅 스크립트에 사용 |

| `bun`, `python3` | 있음 | 각각 Homebrew, pyenv 경로 |

**권장:** 훅은 bash 3.2와 `/usr/bin/jq`로 작성한다. 다른 런타임을 쓸 경우 훅 실행 환경에서 동작하는지 먼저 확인한다.

### 5.9 설치
로컬 경로를 마켓플레이스로 추가한 뒤 플러그인을 설치한다. 정확한 명령은 빌더가 공식 문서로 확인한다.

### 5.10 과금 제약: 구독 전용 (사용자: API 과금 절대 배제)
이 도구가 부르는 모든 모델 호출(검증 실행기, 시범 평가)은 구독 요금제의 사용량으로만 처리한다.

**강제 방식 (판단: 반목표 A6을 지시문이 아니라 코드로 막기 위함)**
- **실행기 등록 조건:** 실행기마다 다음 네 가지를 담은 **과금 확인 기록**이 있어야 한다. 기록이 없는 실행기는 `ga`가 실행하지 않는다.
  1. 구독 인증 방식
  2. API 과금으로 바뀌게 만드는 환경변수나 설정
  3. 실행 전 점검 명령
  4. 확인한 출처 URL과 확인 날짜
- **실행 전 점검:** 호출할 때마다 점검하고, 실패하면 실행하지 않는다. "점검이 안 되면 실행하지 않는다"가 기본값이다.
- **기록 갱신:** 과금 정책은 바뀔 수 있다. 그래서 과금 확인 기록에는 확인 날짜를 남기고, 시범 평가 전에 다시 확인한다.

**Claude 실행기 (v1)**

| 항목 | 내용 | 출처 |
|---|---|---|
| 구독으로 처리되는가 | 요금제로 로그인한 상태의 `claude -p`는 구독 사용량에서 차감된다 | 확인: Claude 지원 문서 "Use the Claude Agent SDK with your Claude plan" |
| API 과금으로 바뀌는 조건 | `CLAUDE_CODE_USE_BEDROCK`/`VERTEX`/`FOUNDRY`, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_API_KEY`, `apiKeyHelper` 설정. 특히 `ANTHROPIC_API_KEY`는 `-p` 모드에서 **있으면 항상** 쓰인다 | 확인: Claude Code 문서 Authentication의 인증 우선순위 |
| `--bare` | 구독 인증(OAuth)을 읽지 않으므로 사용 금지 | 확인: Claude Code 문서 Headless |

점검 순서:
1. 자식 프로세스 환경에서 위 환경변수를 **제거**한다.
2. 설정 파일에 `apiKeyHelper`가 있으면 실행을 **거부**한다.
3. `claude auth status`의 `authMethod`가 `claude.ai` 또는 `oauth_token`(구독용 장기 토큰)일 때만 실행한다. (확인: CLI 레퍼런스)

이 기기의 현재 상태:
- API 키 관련 환경변수 없음
- `apiKeyHelper` 설정 없음
- `authMethod=claude.ai`

**다른 실행기와 어댑터 (이후 단계, 만들 때 다시 확인)**

| 대상 | 구독 경로 | API 과금 경로 | 현재 판단 |
|---|---|---|---|
| Codex CLI | ChatGPT 로그인 시 요금제 크레딧 사용 (확인: OpenAI Codex 인증 문서) | API 키로 로그인하면 API 요금 | 사용 가능 후보. `codex login status`로 ChatGPT 로그인인지 확인하고, `OPENAI_API_KEY`를 제거한다. 다만 오래된 버전에서 ChatGPT 로그인 시 API 키가 자동 생성됐다는 보고가 있어 다시 확인한다 (GitHub openai/codex 이슈 #2000). 이 기기의 `codex`는 실행 파일이 없어 지금 동작하지 않는다 |
| OpenCode | ChatGPT Plus/Pro 로그인, GitHub Copilot 구독 (확인: OpenCode 제공자 문서, GitHub 변경 기록 2026-01-15) | API 키 | 구독 제공자만 허용한다. **OpenCode에서 Claude 구독을 쓰는 것은 제외한다.** OpenCode 문서에 Anthropic이 이를 금지한다고 적혀 있다 |
| Gemini, Grok | 확인 안 됨 | 확인 안 됨 | 구독 경로를 확인하기 전까지 실행기 등록을 금지한다 |

**기타**
- **훅 종류:** 훅은 `command` 종류만 쓴다. `prompt`나 `agent` 종류 훅이 어떻게 과금되는지는 문서로 확인되지 않았기 때문이다. (확인: Hooks 레퍼런스에 과금 기술 없음)
- **대안 경로도 구독이다:** 대안 경로인 Claude 서브에이전트는 세션의 사용량에서 차감된다. (확인: Claude Code 문서 Costs)
- **메인 세션 점검:** 메인 세션 자체가 API 키로 돌고 있으면 SessionStart 훅이 경고를 넣는다. 메인 세션의 인증은 사용자가 정하는 것이라 차단하지는 않는다. (판단)
- **약관:** Anthropic은 제3자 제품이 claude.ai 로그인을 제공하는 것을 허용하지 않는다(확인: Agent SDK 문서). 사용자 본인의 스크립트에서 `claude -p`를 쓰는 것을 금지한다는 문서는 찾지 못했다. 이 플러그인을 다른 사람에게 배포할 때는 약관을 다시 확인한다. (가정)

## 6. 성공 기준과 검증

**1. 게이트 스크립트**
- 입력 JSON을 넣었을 때 기대한 결정(허용, 거부, 차단)이 나오는지 단위 테스트한다.
- 게이트마다 "막아야 할 실제 사례가 실제로 막히는지"를 테스트로 증명한다. (pstack correct의 "실제 과거 실수로 실패를 증명" 원칙을 차용)

**2. 설계 품질 시범 평가**
- **대상:** ADD 논문의 Event Ticketing System. 드라이버(비전, 품질 속성 시나리오, 우선순위)가 공개되어 있다: https://github.com/otrebmuh/EventTicketSystem
- **비교:** 플러그인 사용 vs 미사용
- **측정:**
  - 드라이버 충족 여부 (충족, 부분, 미충족)
  - 근거 없는 판단의 수
  - 결정 간 모순의 수
- **이 사례를 고른 이유:** 드라이버와 논문의 평가 결과가 공개되어 있어 비교 기준이 있다. (판단)
- **진행 방식** (판단, 빌더 검토 Q11)
  - **완료 조건에 포함:** 이 시범 평가는 v1 완료 조건에 들어간다.
  - **이해관계자 역할:** 플러그인이 던지는 질문에는 공개된 드라이버 문서에 있는 내용으로만 답한다. 문서로 답할 수 없는 질문은 "답 없음"으로 기록한다. 이렇게 하면 질문이 적절했는지도 평가 대상이 된다.
  - **채점:** 별도 채점 에이전트가 세고, 사용자가 일부를 표본 확인한다.
  - **합격 기준치:** 첫 측정 후 사용자와 정한다.
- **기존 코드용 시범 사례**
  - Event Ticketing은 새 프로젝트라서 기존 코드 모드를 시험하지 못한다.
  - 사용자의 기존 프로젝트 중 하나를 쓴다. 사용자가 정답을 알고 있어서 채점 기준이 생기기 때문이다.
  - 어떤 프로젝트를 쓸지는 구현 계획 단계에서 사용자가 고른다.

**1-1. 과금 점검 테스트**
- 아래 각 조건을 넣었을 때 Claude 실행기가 해당 변수를 제거하거나 실행을 거부하는지 테스트한다.
  - `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `CLAUDE_CODE_USE_*`
  - `apiKeyHelper` 설정
  - `authMethod`가 `api_key`인 경우
- 과금 확인 기록이 없는 실행기를 `ga`가 거부하는지 테스트한다.

**2-1. 호출 충돌 확인**
- `/design-architecture`를 직접 호출했을 때 superpowers brainstorming이 끼어들지 않는지 확인한다.
- 5.3.0절의 가정을 검증하는 항목이다.

**3. 공통 규칙 주입의 효과**
- 플러그인 사용 전과 후에 같은 프롬프트 N개를 돌려, 근거가 표시된 판단의 비율을 비교한다.
- 합격 기준치는 아직 정하지 않았다. (가정) 측정한 뒤 사용자와 정한다.

## 7. 알려진 한계와 위험
- **형식 검사의 한계:** 형식 검사는 근거의 내용을 보지 못한다. 반목표 A3 방어는 검증 에이전트에 달려 있다.
- **셸 우회:** Bash를 통한 쓰기는 완전히 막을 수 없다 (G-bash).
- **종료 게이트 상한:** Stop 게이트는 연속 8번 막으면 해제된다.
- **게이트의 상시 실행:** 게이트가 플러그인 수준이라 모든 프로젝트의 모든 도구 호출에서 실행된다. `.state`가 없으면 즉시 통과하게 만들어 대응한다. 실행 시간은 측정이 필요하다.
- **주입 규칙의 준수율:** 검증되지 않았다. 참고로 pstack에서는 시작 시 넣은 지시를 따른 비율이 19%였다(#264). 다만 이는 한 사용자, 한 기기의 관찰치이고 원인은 검증되지 않았다.
- **비용:** 반복마다 검증 에이전트를 실행하므로 비용이 든다 (반목표 A4). 시범 평가에서 시간과 토큰을 함께 기록한다.
- **어댑터별 강제력 차이:** 다른 하네스에서는 일부 게이트를 강제하지 못할 수 있다 (5.0절).
- **과금 정책 변경:** Claude 지원 문서에는 `claude -p` 사용량을 별도 크레딧으로 분리하려다 보류했다는 기록이 있다(2026-06-15). 정책이 바뀌면 구독 사용이 불가능해질 수 있다. 과금 확인 기록의 날짜로 이를 추적한다.
- **CLI 경로:** `codex` 같은 다른 모델 CLI가 nvm 경로에 있어서, 훅이나 스크립트 실행 환경의 PATH에서 찾지 못할 수 있다. 실행기는 절대 경로 설정을 지원해야 한다.
- **brainstorming의 선점:** 사용자가 명령어 없이 "설계해줘"라고만 하면 superpowers brainstorming이 먼저 실행될 수 있다. 대응은 명령어로 직접 호출하는 것이다.
